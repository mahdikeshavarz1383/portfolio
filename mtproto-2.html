MTProto

Telegram's own transport protocol, and how to run your own MTProto proxy on a VPS.

What is MTProto?

General overview — expand this with anything you've learned that isn't covered yet.

MTProto is the custom protocol Telegram uses for client-server communication, instead of relying on plain TLS like most apps. It handles encryption, authentication, and message transport itself.

An MTProto proxy is a lightweight relay you run on your own server. Telegram clients connect to your proxy instead of connecting to Telegram directly; the proxy then forwards traffic to Telegram's data centers. Because the connection to your proxy doesn't look like a connection to Telegram, this is commonly used to get around network-level blocking of Telegram's own IP ranges.

Unlike a VPN, it only proxies Telegram traffic — not your whole system — which is part of why it's cheap to run on a small VPS.

  • Proxy vs VPNA VPN tunnels all traffic; an MTProto proxy only tunnels Telegram's traffic, so it needs far less CPU/RAM.
  • SecretThe per-user key clients use to connect. Anyone with it can use your proxy, so treat it like a password.
  • Fake-TLSA mode where the proxy disguises its traffic as a normal HTTPS connection to a real-looking domain, making it harder to fingerprint and block.
  • AD_TAGAn optional tag from @MTProxybot that lets you advertise a Telegram channel to people using your proxy.

How to run MTProto on a VPS

Using alexbers/mtprotoproxy — a well-maintained, widely used (500K+ pulls) Python implementation that ships with Docker Compose support out of the box.

Recommended minimum VPS specs:

  • OS: Ubuntu (22.04 or newer)
  • Resources: 1 vCPU / 1 GB RAM — comfortably handles a few thousand simultaneous users
  • Region: Netherlands or Germany (or wherever gives the best latency/least filtering for your users)
1

Update packages and install Docker

sudo apt update
sudo apt install -y docker.io docker-compose

fixed: plain "docker" isn't a real apt package on Ubuntu — it's docker.io (the engine) plus docker-compose.

2

Enable and start the Docker service

sudo systemctl enable --now docker

added: without this, later commands fail with "cannot connect to the Docker daemon".

3

Clone the proxy repo

git clone -b stable https://github.com/alexbers/mtprotoproxy.git
cd mtprotoproxy
4

Edit the config

nano config.py

Set PORT, USERS, and optionally AD_TAG (from @MTProxybot).

5

Open the port on the firewall

sudo ufw allow <PORT>/tcp

added: this step was missing — without it, the port is reachable from inside the VPS but blocked from the outside.

6

Build and start the container

sudo docker-compose up -d --build
7

Verify it's running

sudo docker ps

You should see the mtprotoproxy container listed as Up.

8

Get the shareable proxy link

sudo docker-compose logs

The proxy link (with the secret baked in) is printed in the logs — this is what you share with Telegram clients.

Troubleshooting Log

Your own MTProto cases go here, same format as the main site's log.

#MTP-001checklistdocker · firewall · networking

Proxy container is "Up" but Telegram can't connect

Symptom: docker ps shows the container running, but clients can't connect to the proxy. Since the container itself is healthy, the problem is usually somewhere between the client and the service.

likely causes (check in this order)

1. Firewall: ufw is blocking the port, or a separate firewall in the VPS provider's panel is.

sudo ufw status
sudo ufw allow <PORT>/tcp

2. Port conflict: another service is already using the same port. This shows what is actually listening:

sudo ss -tlnp | grep <PORT>

3. Port mismatch: the port in config.py doesn't match what docker-compose.yml exposes (ports or network_mode). The container stays Up, but traffic never reaches the service.

cat docker-compose.yml
sudo docker-compose logs

4. ISP blocking the port: test from a different network (e.g. a mobile hotspot). If it connects from one and not the other, the problem is the ISP path, not the server. ping isn't suitable here since it doesn't test a specific port; from an outside machine use:

nc -zv <IP_VPS> <PORT>

fix

If the port is the problem, change it in config.py, open the firewall for the new port, then bring the container up again so the change applies:

nano config.py
sudo ufw allow <NEW_PORT>/tcp
sudo docker-compose up -d --build
